# The Concept Canvas

*Design direction, July 2026. Supersedes the panel-per-app IA.*

## The one sentence

> Docent is a canvas where any concept unfolds to the depth you need — grounded in what
> you've actually read — with an assistant that can see what you're looking at.

Everything below serves that sentence. Anything that doesn't is a candidate for deletion.

---

## Why this rewrite exists

The app is ~40 services and ~30 panels deep, and the two things that felt weakest in
daily use were screen perception and tool calling — the two hardest problems in the
category. But the actual diagnosis, on review, was different: **the knowledge substrate
is good and under-used.** The graph, the closed vocabulary, the shelves, the evidence and
confidence fields all exist and are correct. What was missing was a center of gravity for
them to hold up.

`graphContext.ts` already records the previous rung of this same ladder — the graph went
from *"a picture, not a memory system"* to something read back into answers. This is the
next rung: from **memory** to **understanding**.

The substrate does not get rebuilt. It gets a subject.

---

## The primitive

A **Concept** is the new unit. Not a graph node (that's a thing that was named) and not a
note (that's a thing that was written). A concept is a thing that can be *understood*, and
understanding has exactly one universal axis: depth.

```ts
type Rung = 'orient' | 'working' | 'deep' | 'frontier';

interface Concept {
  id: string;
  label: string;
  facets: Partial<Record<Rung, Facet>>;   // generated lazily, cached
  threads: Record<string, Facet>;          // generated on pull, cached
  // Connections and sources are NOT stored here — they are read live from the
  // graph and the semantic layer, so a concept never goes stale against them.
}

interface Facet {
  blocks: Block[];
  invites: string[];        // questions THIS concept raises at THIS rung
  generatedAt: number;
  model: string;
}

// A grounded block is STRUCTURALLY unable to exist without its evidence. Optional
// fields plus a comment saying "required when…" is how the rule gets skipped under
// deadline; a discriminated union makes the compiler enforce it.
type Block =
  | { origin: 'read' | 'authored'; text: string; sourcePath: string; quote: string }
  | { origin: 'observed';           text: string; frameId: string;    seenAt: number }
  | { origin: 'generated' | 'contested'; text: string };
```

Each grounding variant carries the evidence that makes it checkable, and the compiler will not
let you claim grounding without it: a source sentence for `read`/`authored`, a frame and a
timestamp for `observed`. `generated` and `contested` carry no evidence because there is none
to carry.

`quote` is the sentence in the source that the block relies on, and it is what makes a
grounded block *checkable* rather than merely *labelled* (§Delta ③). `text` may contain
`{{thread}}` pull-points in any variant.

### Rejected: the lens axis

An earlier draft had a second axis — Mechanism / Origins / Tension / Practice — as tabs.
It was cut, and the reason generalizes: **a fixed grid applied to every concept is a
taxonomy, not a docent.** Prompt injection, grief, and the French Revolution do not
decompose the same way. A real docent follows what you lean toward; it does not announce
the Origins tab.

What replaced it: **threads**. Pull-points inside the prose, plus per-rung `invites` — both
generated by the concept rather than imposed on it. Contested claims no longer need a home
tab; they carry a doubled stripe wherever they appear, because disagreement is a property of
a claim, not a place you visit.

This is also cheaper: four rungs per concept instead of sixteen cells, and threads cost
nothing until pulled.

## Provenance is typed, not just stored

The load-bearing rule of the whole design.

| `Origin`    | Meaning                              | Retrievable | Counts as grounding | Stripe          |
| ----------- | ------------------------------------ | ----------- | ------------------- | --------------- |
| `read`      | An external source actually ingested | yes         | **yes**             | solid           |
| `authored`  | The user wrote or corrected it       | yes         | **yes**             | solid           |
| `observed`  | The screen log saw it                | yes         | **activity only**   | solid, scoped   |
| `generated` | The docent produced it               | yes         | **never**           | dashed          |
| `contested` | Sources genuinely disagree           | yes         | no                  | double / hatched |

`observed` is the screen log, and it grounds claims about *your activity* rather than about the
world — see §The screen log. It never auto-promotes to `read`.

### Provenance is encoded in FORM, not hue

Learned by running the app rather than reading it: the accent is **user-selectable across ten
themes** (`[data-accent='lavender'|'jade'|'coral'|'blue'|'pink'|'amber'|'emerald'|'cyan'|
'violet'|'rose']`, `index.css:246+`; lavender `#6b4ce6` / `#8e73ff` is the default). Earlier
drafts of this design coded provenance by color — green for grounded, purple for the docent.
That collides: a user on `jade` or `emerald` gets chrome in the same green that is supposed to
mean "from your library"; `violet` collides with "the docent's own knowledge."

So the **stripe shape is load-bearing and the tint is decoration**. Solid means checkable,
dashed means the model said it, doubled means sources disagree — legible on every accent theme,
and legible to colorblind users, which a hue-only scheme never was. Any tint should come from
the semantic tokens (`--af-success` / `--af-warning`), never from `--af-accent`.

### What the model is for — the capability boundary

The `Origin` rule is not a policy preference. It falls out of what the technology can and cannot
do, and the research is unusually settled on this.

**A model's own memory cannot ground anything.** Hallucination is structurally inevitable, not a
defect awaiting a patch: Gödel-style arguments establish true facts beyond any finite training
set, so no fact-checking corpus can be complete — and even given complete data, models cannot
retrieve correct information deterministically. Worse for our purposes, models cannot report
their own reliability: internal states "mainly reflect knowledge *recall* rather than
truthfulness," so self-assessed confidence is not a truth signal. Reported factual hallucination
rates across six major models run 59–82% on hard factual benchmarks.

**But models are reliable in one specific regime**, and every task Docent actually needs sits
inside it:

> A model is reliable exactly where its output can be checked against something outside the model.

Source-conditioned tasks (extraction, summarization, reorganization, connection-finding) measurably
outperform open-ended generation, because open-ended generation is the case where the model must
draw on internal knowledge. *Verification asymmetry* — checking a solution is cheaper than
producing one — is why code iteration works: there is a compiler. The practitioner's question is
"what's the compiler here?" For Docent the compiler is the user's own library.

So the model's job description is narrow and stated positively:

| Docent's model DOES | Docent's model NEVER |
| ------------------- | -------------------- |
| Transform, summarize, and re-level what you read | Supply a fact from its own memory as grounding |
| Extract entities and relations from a source | Assert its confidence as evidence |
| Find and rank connections across the library | Verify its own output |
| Organize, structure, and re-format | Fill a gap in your library silently |
| Draft, then iterate against a check | — |

Two consequences that are easy to get wrong:

1. **Citation checking must be mechanical.** A model asked to verify its own output "will often
   agree with itself, not because it has checked carefully, but because the same model acting as
   generator, evaluator and critic tends to reproduce the same reasoning structure." So Delta ③'s
   check is a **string match of `Block.quote` against the source text** — never a model judgement.
   A quote that no longer matches is reported as stale (see `knowledgeHealth.ts`), not re-judged.
2. **Verification has latency, and unverified claims propagate.** A block must not render with a
   solid (grounded) stripe until its quote has actually matched. Render it dashed and upgrade it,
   never the reverse.

**This is why moving to local models is the right call, not a compromise.** Smaller models verify
better than they generate. Docent's real work — transform, extract, organize, check — is the
verification-shaped half of the job. A local model that would make a poor oracle is well matched
to the task actually being asked of it, and the `Origin` rule means a weak model cannot damage the
library no matter how badly it performs: its output was never permitted to ground anything.

### Why `generated` must never count

Everything the docent produces is retrievable — concepts persist, feed search, and feed the
dream cycle. But if generated text were allowed to *ground* a later claim, the app would
cite its own prior output back to the user as if it were knowledge. The grounding meter
would climb toward 100% while actual sourced knowledge stayed flat. Model output would
launder itself into apparent user knowledge, one hop at a time.

This is measured, not hypothetical. In RAG systems running as a closed loop **without
provenance tracking**, a corpus starting at ~13% synthetic content reaches **50% within ~17
generations** and stabilises around **72%** — and RAG *accelerates* the drift rather than
damping it. The reason it goes unnoticed is the part that matters here: answer quality holds
up throughout, because fluency survives even as grounding drains away. The erosion has to be
measured; it cannot be noticed.

A `generated` block keeps its dashed stripe until something `read` supports it. **The library
gains grounding only from reading and writing.** This single rule is what keeps the meter
honest, and it is far cheaper to enforce now than to unwind later.

### The grounding meter

Per rung: `grounded = (read + authored) / total`. Shown as a two-part bar with the split
stated in words. Its real job is not reassurance — it is showing you **the edge of what you
know**. In practice the curve runs high at Working and hits zero at Frontier, which is
correct and should not be smoothed.

At 0% grounded, the meter is replaced by the on-ramp: *"You own none of this yet — go read?"*
That is the primary entry point for a new concept, not an error state. Reading feeds
`pageDigest` → `graphEntityExtractor` → gatekeeper, and blocks convert from dashed to solid
as sources land.

### The monitor: `knowledgeHealth.ts` — BUILT

`Origin` typing is the *guard* — it stops the loop closing. `src/services/knowledgeHealth.ts`
is the *monitor* that proves the guard is holding, and catches the softer failures the guard
does not cover. Built and tested (17 tests, `src/tests/services/knowledgeHealth.test.ts`);
pure, no callers yet, and it cannot produce real numbers until `Origin` exists to count.

It deliberately mirrors `contextHealth.ts` — same pure-function shape, injectable clock,
`status / headline / detail / recommendations`, and the same refusal to be a fullness bar.
Two design calls worth preserving:

- **It measures drift, not level.** A high generated share is what *learning something new*
  looks like, so there is an explicit `exploring` status that stays quiet while you are
  reading into fresh territory. What trips `attention` is grounded share **falling while the
  library grows** — the closed-loop curve above, caught early. A prior `KnowledgeSnapshot`
  is an input precisely so direction can be measured rather than inferred.
- **Source diversity catches what a ratio cannot.** A library that is 100% grounded but
  traces everything to two pages reads perfectly healthy as a percentage and is not —
  "retrieval collapse" erodes source diversity before it erodes accuracy.

`facetsFromRetiredModels` exists for the move to local models: passages written by a model
you have since replaced can be found and regenerated, and **nothing is lost by regenerating
them, because none of it was ever grounding anything.**

## Perception is the intake path

Browser reading and screen reading are not retained as features — they are **promoted to
load-bearing**, because they are the only machinery that converts a `generated` block into a
`read` one. Without them the grounding meter can never move, and the app is just a
confident chatbot with a nice layout.

Stays core:

- **Screen** — `capture_screen_text` (on-device Apple Vision OCR), `desktopVision.ts`, the
  glow-pulse capture receipt, and the read already wired at `SpotlightBar.tsx:503`.
- **Browser** — `browserAgent.ts`, `pageCapture.ts`, `pageDigest.ts`, `browser_snapshot_text`,
  `browserAnnotator.ts`.

The on-ramp button ("Go read this →") is not new work: it is
`browserAgent` → `pageDigest` → `extractAndWriteGraph`, wired today at `pageDigest.ts:112`.

**Open:** `BrowserPanel.tsx` + `BrowserTabContent.tsx` are ~1.6k lines of tabbed-browser UI.
By the "no apps, just a canvas" principle that is an app panel. Reading must stay; the
browser-as-application probably slims rather than dies. Unresolved.

### The screen log — `observed`, a fourth Origin

Perception above is *on demand*: you ask, it looks. The log is the other half — a continuous,
low-cost record of what was actually on screen, kept as its own kind of knowledge.

This is a proven category rather than a research bet: Recall (5s sampling into a searchable
3-month store), screenpipe (24/7, fully local), Windrecorder. Storage runs ~300 MB per 8 hours
as JPEGs. The technique they all converged on is the one already written down in the June
notes: **accessibility tree first, OCR as fallback.**

**A screen log grounds your history, not the world.** This is the distinction the whole
feature turns on. The log is excellent evidence for "I was looking at X on Tuesday" and poor
evidence for "X is true" — you saw a page; you did not necessarily read it, agree with it, or
check it. Hence a fourth `Origin`:

| `Origin`   | Grounds                    | Checkable against          | Stripe |
| ---------- | -------------------------- | -------------------------- | ------ |
| `read`     | claims about the world     | the source document        | solid  |
| `authored` | claims about the world     | your own note              | solid  |
| `observed` | claims about your activity | the frame + timestamp      | solid, but scoped to activity |
| `generated`| nothing                    | —                          | dashed |

`observed` is genuinely checkable — there is a frame and a timestamp — which makes it
categorically unlike `generated`. But it **must never auto-promote to `read`**: screen content
is untrusted (§poisoning hazard), and seeing is not reading.

#### The model is never in the capture path

Three tiers, ordered by cost. This is what makes always-on affordable, and it is the direct
answer to the July "eyes vs hands" performance objection — that objection was about piping 12k
OCR dumps through a model on every turn. A log does not do that.

| Tier | What runs | Model? | When |
| ---- | --------- | ------ | ---- |
| 0 · Capture | change-triggered frame → AX tree / on-device OCR → local index | **no** | always |
| 1 · Recall | search the index; return frames + text | **no** (or cheap embed) | on demand |
| 2 · Enrichment | entities, recurring themes, promotion proposals | yes — **local, batched** | dream cycle, idle |

The sampler already exists: `computeGridHashes` + `hasFrameChanged` in `desktopVision.ts`
already detect *meaningful* screen change. Capture on change, never on a timer — most frames
are chrome and navigation, and that filter is the difference between a log and noise.

#### Enrichment belongs to the dream cycle

Deferring tier 2 to `dreamer.ts` is what keeps this cheap, keeps it local, and keeps it honest.
Batched idle-time enrichment can afford a slower local model, and the existing dream-consent
gate already covers it — `dreamAutoEnabled` stays false by default per the standing decision.

The hard constraint on enrichment: **it may create `observed` entries and *proposals*, never
`read` facts.** The dream cycle noticing you returned to a page fourteen times is a proposal —
*"you keep coming back to this; want me to read it properly?"* — and accepting it is what runs
the real read path and produces grounding. Enrichment that wrote `read` facts directly would
re-open the poisoning hole from the other side.

That loop is the payoff, and it is the "quick capture" strength wired into the grounding model:

> **observe → recall → promote → ground**

Nothing is filed deliberately. The log catches it; later, the thing you keep returning to gets
promoted into the library and starts grounding claims.

#### Exclusions are built first, not retrofitted

Every product in this category learned the same lesson expensively: Recall shipped capturing
passwords, banking and private messages. The convergent answer is exclusion lists (password
managers, banking, private windows), optional PII redaction, local-only storage, encryption.

Build the exclusion list **before** the capture loop. Retrofitting means the log already
contains exactly what should never have been in it, and there is no un-seeing it. This is the
line between a memory tool and a keylogger.

#### Scope note

`knowledgeHealth.ts` measures **the library**, not the log — they are separate corpora with
separate jobs, so no change is needed there when `observed` lands. If the log ever gains its own
health signals (capture gaps, exclusion coverage, promotion rate), they belong in their own
module rather than muddying the grounded/generated ratio.

### The poisoning hazard this design creates

`pageDigest.ts:112` fires `extractAndWriteGraph` over the page's raw `cleanText`,
fire-and-forget. The extractor's only guard is `sanitizeEntityId` — slug hygiene, not trust.
Untrusted web content can therefore write entities and relations into the graph. Three of the
four extraction callers (`pageDigest`, `KnowledgeDropZone`, `conversationGraph`) carry
untrusted or semi-trusted text.

That is already true today and is survivable, because those nodes only sit in a graph panel.
**The concept canvas changes the consequence:** extracted claims become *grounding*, rendered
with the solid stripe that means "checkable, and yours." A page crafted with plausible facts
would be cited back to the user months later as their own knowledge. Prompt injection stops
being a one-turn steering problem and becomes permanent knowledge-base poisoning. The trust
model §3 escalation guards *actions*; nothing currently guards *what gets believed*.

Mitigations, in order of cheapness:

1. **Delta ③ does double duty.** A solid stripe that must show the actual sentence and click
   through to its source exposes a poisoned claim as coming from `randomblog.example`. A
   filename hides that; a quote cannot. Designed as an anti-overtrust measure, it is also the
   injection defense — a decent signal it is the right primitive.
2. **Extraction provenance is already recorded** (`sourceNodeId`, `sourceUrl`), so poisoning
   is traceable and revocable. Needs a user-facing "forget everything from this source."
3. **Single-source claims should ground weakly.** Corroboration across independent sources is
   the difference between a fact and a page that said so once.

## What the research says

Checked before building, including evidence against. The findings on what a model can and
cannot be trusted to do live in §What the model is for; the findings on corpus drift live in
§Why `generated` must never count. This section covers the *learning-design* claims.

**Backed:**

- **The depth ladder.** The *expertise reversal effect* is well replicated: instructional
  support that helps a novice becomes counterproductive as expertise grows — redundant
  explanation is extraneous cognitive load for someone who already holds the schema. One
  explanation for all readers is a known failure mode.
- **Threads over taxonomy.** Self-generated question-asking drives curiosity-driven
  learning; "wonderment" questions specifically trigger reflection, skepticism and
  speculation. Learner-chosen direction produces higher-quality questions than an imposed
  frame.
- **Progressive disclosure** is established practice — with the caveat below.

**Against, and taken seriously:**

- **Citations induce trust rather than calibrate it.** Users trust LLM output containing
  references even when the references are fabricated or irrelevant. Frontier models show
  >94% link validity and >80% topical relevance against only 39–77% factual accuracy.
  A provenance mark is therefore a *credibility badge* by default, which is the opposite of
  the intent — the fix is that it must be checkable, not prettier. → Delta ③.
- **Cognitive offloading produces an illusion of competence.** AI fluency encourages
  "metacognitive laziness"; there is a documented speedup illusion (effort drops, time
  does not) and a feedback loop where saved effort miscalibrates perceived benefit and
  drives more offloading. Progressive disclosure itself was found to raise *perceived*
  learning without reducing cognitive load.
- **The generation effect** (d ≈ 0.40 across 86 studies) favours producing an answer over
  receiving one — and **a failed attempt followed by feedback still beats being told.**
  A tool that unfolds any concept on demand is, unmodified, a machine for being told.
  → Delta ②, Delta ④.

## Deltas that follow from the research

**① Open at the right rung.** Do not default to Orient. The graph already knows the user's
prior knowledge on a concept — source count, edge degree, dossier presence. Twelve saved
posts on prompt injection means opening at **Deep**. This is the app's structural advantage:
nobody else can calibrate teaching against the user's own library. *Smallest of the four,
build first.*

**② Some threads ask before they tell.** Not all — that is exhausting. But on a thread
pulled at or below the user's own depth, a beat of *"before I answer — what do you think?"*
converts a receiving moment into a generating one. Ship behind a setting; this changes what
the product feels like, and a docent that occasionally asks is a different experience from
one that only answers.

**③ Solid means checkable, not true.** Because a citation induces trust regardless of
validity, a grounded block must be **one click from the actual sentence** it relies on —
hence the required `quote` on the grounded variant of `Block`. A filename is a badge; a quote
is a verification affordance. Uncertainty must render louder than provenance, never quieter.

Two requirements that are easy to lose and expensive to retrofit (see §What the model is for):

- **The check is a mechanical string match** of `quote` against the source text. Never a
  model judgement — a model verifying its own output agrees with itself.
- **Blocks render dashed until the quote matches, and upgrade to solid — never the reverse.**
  Verification has latency, and a claim shown as grounded before it is verified has already
  been believed by the time the check returns.

**④ Retrieval closes the loop.** Reading builds nothing durable without recall.
`dreamer.ts` and the existing consent flow are the natural home: resurface previously
unfolded concepts **as questions**, days later. Unfold → dream → recall. Keep
`dreamAutoEnabled` false by default per the existing decision; this is the funnel's payoff,
not a reason to flip it.

## What stays, what goes

**Untouched.** Rust commands, the SQLite graph, the Knowledge Core files, extraction,
semantic search, the memory gatekeeper, evidence/confidence, receipts, the trust model and
its approval gates. Not one byte of the knowledge base is migrated or dropped — see the
never-wipe policy in `agent-model-rollout.md`.

**Promoted.** `SpotlightBar.tsx` is already a separate window with its own event bus, screen
OCR, memory retrieval and playbooks. It becomes the primary way in: point at anything on
screen, unfold it. `EntityDossierPage.tsx` is the concept canvas's direct ancestor and is
where the new view should start.

**Retired from the UI.** The Mail, Calendar, Planner and Messages panels — the
assistant-does-chores product. Roughly 3.5k lines of panel code.

**Kept but unrouted.** `mail.rs`, `calendar.rs`, `imessage.rs` and their connectors. The
docent still *reads* mail and calendar as context ("this message is about the vendor
contract you saved a note on"). What goes away is the surface that imitates Mail.app. The
reading capability stays; the chore UI goes.

## Build order

Deliberately sequenced so each step is shippable alone and the early ones are small. The
original complaint was that the app felt like too much to work on — this order exists to
make that false.

0. ~~**Knowledge health monitor.**~~ **DONE** — `knowledgeHealth.ts` + 17 tests. Built ahead of
   order because it is zero-risk and pure; it stays inert until step 1 gives it something to
   count.
1. **Provenance typing.** Add `Origin` and the discriminated `Block` union, and enforce that
   `generated` never grounds. Pure, testable, no UI. Cheapest now, most expensive if
   deferred. *(§Provenance)*
2. **Concept + Facet, one rung.** Render `orient` for a concept, using the existing graph
   read for connections and the semantic layer for sources. Reuses `EntityDossierPage`.
3. **Delta ③, with the first solid stripe ever drawn.** Carry `quote` through, verify it by
   mechanical string match, and make a grounded block click to its actual source sentence.
   *Moved up from step 6: this is not polish. Solid is the trusted form, and a solid stripe
   that cannot be verified is the poisoning hazard above. Never ship a grounded render
   without a matched quote.*
4. **The ladder.** Three more rungs, lazily generated and cached.
5. **Delta ①.** Choose the opening rung from graph signal. Small, high payoff.
6. **Threads.** Pull-points and per-rung invites. Cached on pull.
7. **Popover entry.** Spotlight → "unfold this" against screen selection or OCR.
8. **Panel retirement.** Only after the canvas carries daily use.
9. **Delta ④.** Dream-cycle recall over unfolded concepts.
10. **Delta ②.** Ask-before-tell, behind a setting. Evaluate against 9.

**The screen log is a parallel track, not a step in this sequence.** It shares the `Origin`
type from step 1 and nothing else, so it can proceed independently once step 1 lands. Its own
order is fixed and non-negotiable: **(a) exclusion list, (b) change-triggered capture + local
index, (c) recall UI, (d) dream-cycle enrichment and promotion proposals.** (a) before (b),
always — see §Exclusions are built first.

## Ground truth about the shell

Established by running `npm run dev` and reading the live accessibility tree — not by reading
components. Several earlier assumptions in this document were wrong until this pass.

- **There is no sidebar.** `AppSidebar.tsx` does not render: `newShellEnabled` defaults true and
  is force-set at `useSettingsStore.ts:343`. Any design that budgets for a left nav is wrong.
- **The shell is** `OmniTabBar` (full width) → `p-2 gap-2` work area → one or two panes
  (`rounded-xl border-edge/50`, glass unless the tab is *ambient*, split by a draggable divider)
  → `DockedAgentRail` on the right. The rail is deliberately "a frame, not a surface."
- **The docent already exists.** The rail header reads **"Ask Docent"** behind a Glasses icon,
  with resizable persisted width and collapse-to-rail. The single-assistant face is shipped, not
  pending.
- **The brand mark is glasses** (◯◯), not a robot and not the ember flame the June notes
  describe. Perception, in one glyph.
- **The accent is purple and swappable** — see above. `tailwind.config.js`'s `accent: '#D4AA7D'`
  is dead config; the live value is `--af-accent`.
- Live composer verbs are already `Plan · Canvas · Doc · Web Search · Knowledge Base · Add tools`,
  and `knowledge` is already an `OmniTab` type. The concept canvas is plausibly what that tab
  should have been, rather than a new surface.

Method note for future sessions: read the *live* render path before designing against it. A
component existing in `src/components/` is not evidence that it renders.

## Open questions

- **Are four named rungs one taxonomy too many?** They are predictable and cacheable, which
  is why they survived the lens cut. The alternative is a single "go deeper" action with no
  named tiers — less legible, arguably more honest. Unresolved.
- **Where do the `invites` come from at Frontier**, when the library is empty by definition?
  Currently the docent's own knowledge, which is exactly the case Delta ③ is least able to
  make checkable.
- **Does ② survive contact with real use**, or does being asked a question mid-read simply
  feel like an obstacle? Worth an honest self-trial before shipping it on.
